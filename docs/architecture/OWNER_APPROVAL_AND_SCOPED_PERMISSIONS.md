# Owner Approval and Scoped Permission Lifecycle

**Status:** Security architecture decision  
**Version:** 1.0  
**Applies to:** Sofia Core, Policy Engine, API Gateway & Session Manager, executor registry

## 1. Security objective

An owner approval is a narrowly scoped, single-use authorization decision for one exact action. It is not a general permission, an authentication credential, or a statement inferred from conversation text.

A chat message, assistant-role message, quoted transcript, imported history, local-storage flag, model output, voice transcript, or claimed speaker identity MUST NOT create or satisfy an approval.

The current chat route remains inference-only. This design is preparatory; no approval endpoint or privileged execution is enabled by this document.

## 2. Separate authentication, approval, and authorization

These are distinct checks:

1. **Authentication:** Who is making the request? The principal is derived from a validated identity-provider credential and active server-side session.
2. **Approval:** Did that authenticated principal explicitly approve this exact action, using the required assurance method, within the challenge validity window?
3. **Authorization:** Does current policy permit this principal to perform this capability and operation on this target, with these parameters and limits?

Passing one check does not imply passing the others. A valid approval cannot override a denied policy decision, revoked grant, expired session, risk ceiling, or system prohibition.

## 3. Action binding

Before asking for approval, the Policy Engine constructs a canonical action representation. The approval challenge is bound to:
- authenticated principal;
- active session;
- task reference;
- capability and operation;
- exact target/resource;
- canonical parameters digest using SHA-256;
- policy version and required assurance;
- one-time challenge identifier and expiry.

The canonicalization algorithm must be versioned, deterministic, and shared by the challenge issuer and executor. It must include all security-relevant parameters (for example amount, currency, recipient, destination, device, message body, or file scope). Display-only fields are not authoritative.

If any security-relevant parameter changes, the digest changes and the previous approval is invalid. A new challenge and explicit approval are required.

## 4. Challenge lifecycle

1. An authenticated request proposes an action.
2. The Policy Engine evaluates risk and existing grants.
3. If approval is required, the server creates a cryptographically random, single-use challenge and stores its state server-side.
4. The client displays a human-readable summary derived from the same canonical action, including target and material parameters.
5. The owner explicitly confirms or denies through a trusted UI or supported strong authentication flow.
6. The server verifies session/principal binding, challenge nonce, expiry, action digest, required assurance, and replay state.
7. The server records the decision and creates an approval record only on successful verification.
8. The executor revalidates the approval and policy immediately before execution.
9. On successful authorization for execution, the approval is atomically consumed. It cannot authorize a second execution.

Challenges expire quickly according to policy. Exact durations are configuration, not schema constants. A challenge must be invalidated on logout, session revocation, material action change, policy version invalidation, or explicit cancellation.

## 5. Approved methods and assurance

Supported method identifiers in the contract are:
- explicit in-app confirmation;
- passkey;
- platform biometric protected by the device credential;
- strong identity-provider step-up.

The method used must meet the assurance level required by the action's risk policy. A voice match, wake word, voice transcript, or speaker verification alone is not sufficient for high-risk approval. Biometrics should be verified by the platform/identity provider; Sofia should not collect or store raw biometric templates.

The approval UI must not use preselected confirmation, hidden consent, ambiguous wording, or bundled approvals for materially different actions. Denial, timeout, cancellation, and inconclusive verification fail closed.

## 6. Single-use and replay protection

- Challenge identifiers and nonces are generated by a trusted server using a cryptographically secure random source.
- Store only a protected nonce representation; never log or expose the raw nonce.
- Challenge and approval records are bound to one principal and one session.
- Use atomic compare-and-set or transactional state changes for response and consumption.
- Enforce one-time idempotency for challenge response and execution.
- Reject duplicate, expired, already answered, revoked, consumed, cross-session, or cross-principal challenges.
- The executor recomputes the canonical action digest and compares it to the approved digest immediately before execution.
- A retry after consumption must return the recorded result or a safe conflict; it must not execute again.
- Client clocks and client-generated IDs are not replay controls.

## 7. Scoped permission grants

An approval is not automatically a reusable capability grant. A grant may be issued only by the Policy Engine after approval and policy evaluation explicitly determine that a reusable grant is appropriate.

Every grant must be bounded by:
- principal;
- module and version where relevant;
- capability and exact allowed operations;
- target/resource allow-list or explicit scope;
- data scope;
- risk ceiling;
- call, cost, and time limits where relevant;
- issue and expiry times;
- policy version and grant source;
- approval reference when owner approval was required.

Default to one-time approval for high-risk, financial, medical, legal, identity, external communication, or irreversible actions. Reusable grants require a separate explicit choice and narrow scope. No grant may exceed the owner's approved scope or system policy.

Module manifests and executor declarations are requests for capabilities, not grants. A module cannot grant permissions to itself or another module.

## 8. Execution-time revalidation

Immediately before execution, the Policy Engine must verify:
- authenticated session remains active and sufficiently assured;
- approval is approved, unexpired, unrevoked, and unconsumed;
- principal, task, capability, operation, target, and action digest match;
- applicable permission grant is active and within scope;
- current policy version and risk decision still permit execution;
- budget, rate, call, and time limits remain available;
- executor identity/version is trusted and allowed.

If any dependency is unavailable or any check fails, execution is denied. Do not fall back to model judgment or a client-provided flag.

For long-running or multi-step tasks, each consequential step receives its own authorization check. Approval for one step does not authorize later steps or changed parameters.

## 9. Audit and privacy

Record challenge creation, display/response outcome, approval, denial, expiry, revocation, consumption, policy decision, and execution outcome. Audit events must reference approval/challenge IDs and correlation IDs, include safe reason codes, and avoid raw credentials, nonces, full sensitive payloads, or biometric data.

The audit record should preserve the action digest and a safe display summary or reference sufficient for investigation, subject to data-minimization and retention policy.

## 10. Failure behavior

Fail closed on:
- missing or unverifiable authentication;
- missing or stale session;
- wrong principal/session binding;
- expired or replayed challenge;
- mismatched action digest;
- insufficient assurance;
- denied or inconclusive confirmation;
- revoked/expired grant;
- policy or audit service failure;
- unavailable trusted executor;
- exceeded budget or scope.

Do not reinterpret a failure as consent. Do not execute partially authorized work.

## 11. Migration and implementation gates

Do not expose approval or privileged execution endpoints until all are implemented and tested:
1. identity-provider credential verification and server-side sessions;
2. secure challenge generation and storage;
3. canonical action serialization and digest test vectors;
4. trusted confirmation UI and required assurance flow;
5. atomic one-time response and consumption;
6. policy revalidation at execution time;
7. scoped grant issuance, revocation, and expiry;
8. audit event integrity and secret redaction;
9. cross-principal, cross-session, replay, expiry, parameter-substitution, and concurrency tests;
10. rollback and recovery procedures.

Supabase Auth is not connected. No database, endpoint, client UI, or production configuration is changed by this architecture milestone.

## 12. Explicit non-goals

This milestone defines the contract and rules only. It does not create a live approval workflow, grant any capability, enable external actions, change the current chat route, or deploy services.
