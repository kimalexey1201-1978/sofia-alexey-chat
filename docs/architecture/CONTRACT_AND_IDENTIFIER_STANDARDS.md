# Sofia AI Contract & Identifier Standards

Status: normative architecture standard for new contracts; legacy contracts remain compatible until an explicit migration.
Applies to: all module APIs, inter-module messages, events, registries, persisted records, provider/device adapters and test evidence.

## 1. Version terminology

Sofia distinguishes three version concepts; they must not be conflated.

1. **Schema document version** — `schema_version`, SemVer 2.0.0, identifies the version of a JSON Schema artifact. For current v1 schemas this is `1.0.0`.
2. **Contract/API version** — `contract_version`, SemVer 2.0.0, identifies the externally observable producer/consumer interface. It is declared in module manifests, capability records, integration bindings and compatibility declarations.
3. **Implementation version** — the module's own SemVer 2.0.0 release version. It may change without changing a contract if behavior remains compatible.

The schema document version is not automatically the same as the contract version. A schema may be revised without a breaking API change, but any change to accepted/rejected payloads or semantics must be assessed for contract compatibility.

## 2. SemVer policy

Use SemVer 2.0.0: `MAJOR.MINOR.PATCH[-prerelease][+build]`.
- MAJOR: incompatible wire shape, required-field change, removed/renamed field, incompatible semantic or security behavior.
- MINOR: backward-compatible capability/optional-field addition where consumers safely ignore or support it.
- PATCH: backward-compatible clarification or correction that does not alter accepted wire behavior.
- Prerelease versions are not production-stable unless explicitly approved.
- Build metadata does not affect precedence and must not be used to distinguish authorization or compatibility.

Do not use shortened forms such as `1.0` for new contracts. Legacy `envelope_version: "1.0"` is retained as a legacy wire field until a versioned envelope migration is approved.

## 3. Canonical version fields

New schema artifacts use `schema_version: "1.0.0"`.
New inter-module APIs and capability declarations use `contract_version: "1.0.0"`.
Module manifests use `version: "x.y.z"` for implementation version and declare supported contract versions separately.
Compatibility records must identify both producer and consumer contract versions and evidence.

Never infer a contract version from a filename, branch name, Git tag, module version or deployment date.

## 4. Identifier taxonomy

Identifiers are immutable references, not display labels and not authorization by themselves.

| Entity | Canonical form | Example |
| --- | --- | --- |
| Module ID | reverse-DNS/publisher-scoped lowercase | `com.sofia.translation.engine` |
| Capability ID | lowercase dotted namespace | `translation.text.translate` |
| Contract ID | lowercase dotted namespace | `sofia.messaging.envelope` |
| Provider ID | publisher-scoped lowercase namespace | `com.provider.openrouter` |
| Device ID | opaque locally generated ID | random UUIDv7 |
| Principal ID | opaque identity-service ID | random UUIDv7 |
| Session, task, message, event, grant, approval, decision, run ID | UUIDv7 where generated by Sofia | UUIDv7 |
| Correlation/trace ID | UUIDv7 or W3C trace context ID according to trace boundary | UUIDv7 |
| External reference | opaque, bounded string scoped to its source system | provider-issued reference |

Stable software identifiers (module/capability/contract/provider) are namespaced identifiers and must not be replaced by random UUIDs because they identify a published interface across installations. Runtime instance identifiers are opaque and must not embed personal data, hardware serial numbers, email addresses or other secrets.

Existing UUID-only fields remain valid for their current contracts. New fields should use the canonical entity-specific policy. Do not silently accept a different identifier kind in an existing field; introduce a versioned adapter or contract migration.

## 5. Identifier security

- IDs are not secrets, credentials, proof of identity or permission grants.
- Never authorize based solely on possession or guessability of an ID.
- Verify ownership, issuer, scope and status through the authoritative service.
- Do not reuse identifiers after deletion or revocation.
- Avoid sequential IDs for externally observable resources.
- Normalize stable names to lowercase ASCII and validate against their namespace pattern.
- Do not put names, phone numbers, account numbers or device serials in IDs.
- Treat IDs supplied by clients as untrusted until resolved server-side.

## 6. JSON Schema conventions

- Use JSON Schema Draft 2020-12.
- Every schema has a stable `$id`, title, description and explicit `additionalProperties: false` at security-sensitive object boundaries.
- Use `required` for mandatory fields; do not rely on defaults as if validators mutate data.
- Bound strings, arrays, numeric ranges and payload sizes.
- Use UTC ISO 8601 date-time strings for timestamps.
- Define explicit enums for state and decision fields.
- Use stable machine-readable reason codes; human explanations are separate display fields.
- Avoid arbitrary free-form payloads at trust boundaries. Where extensibility is required, use a named extension object with namespace, version and size limits.
- Schema validation is structural only; business rules, authorization, ordering, expiry and cryptographic verification require runtime enforcement.

## 7. Envelope and message conventions

All new inter-module envelopes must carry:
- envelope schema version and stable contract ID/version;
- message ID and correlation ID; task ID when applicable;
- timestamp and deadline where execution is bounded;
- authenticated source principal/module context resolved by the server;
- target module/capability and exact contract version;
- operation, bounded payload and payload schema reference;
- idempotency key for side-effecting operations;
- authority, policy, consent and grant references where applicable;
- trace context and data classification.

The transport payload must not be allowed to assert its own trusted identity. The gateway derives source identity from authenticated session/service credentials and compares any claimed source metadata against it. References to grants or policy decisions must be resolved server-side and bound to the canonical operation.

## 8. Data classification mapping

Use the four-level classification vocabulary as the canonical sensitivity label:
- `public`
- `internal`
- `confidential`
- `restricted`

Legacy semantic categories such as `user_content`, `personal_data`, `sensitive_data`, `credentials` and `device_telemetry` describe data type, not sensitivity level. They must not be treated as direct equivalents. During migration, retain them as data-category tags and assign a separate canonical classification. Apply the most restrictive classification when combining objects unless a reviewed declassification rule exists.

Suggested default mapping (must be validated by policy and jurisdiction; not an automatic conversion):
- public → public;
- internal operational telemetry → internal;
- ordinary user content/personal data → confidential;
- credentials, private sensor streams and highly sensitive data → restricted.

## 9. Compatibility and evolution

- Consumers must declare the contract versions they support.
- Producers must publish the exact version they emit.
- A registry resolves a compatible pair using a tested compatibility record; it must not guess based on string similarity.
- Breaking changes require a new major contract version and a migration/adapter plan.
- Run producer and consumer contract tests for every supported pair.
- Keep adapters explicit, version-pinned, observable and removable after migration.
- Unknown versions fail closed at security boundaries.
- A schema file changing on a branch does not retroactively change a released immutable contract.

## 10. Legacy migration policy

The current v1 contracts are a mixed initial foundation and are not to be bulk-edited in place. Migration sequence:
1. Freeze this standard as the canonical rule for new contracts.
2. Inventory every existing field and classify it as schema version, contract version, implementation version, stable identifier, runtime ID, data category or sensitivity label.
3. Publish an explicit mapping table for each legacy field.
4. Add compatibility adapters and tests before changing producers or consumers.
5. Introduce a new major envelope contract for the legacy `envelope_version: "1.0"` field; keep v1 consumers operating during transition.
6. Migrate one boundary at a time, dual-read only where necessary, and stop dual-write after verified cutover.
7. Remove legacy fields only in a separately reviewed major-version change with rollback evidence.

## 11. Current status

This standard is normative for new work but has not yet been enforced by code or CI. Existing schemas have not been rewritten in this change. Runtime validation, compatibility registry enforcement and migration tests remain pending.
